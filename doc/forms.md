## 1. 通用约定

### 1.1 字段属性含义

| 属性 | 含义 | 取值 |
| --- | --- | --- |
| 字段 ID | 表单模板内的唯一键，写入 `form_data.fields_json` 的键名 | 小写蛇形，全项目唯一 |
| 标签 | 界面显示名称（中文） | — |
| 类型 | 控件与值类型 | text / textarea / number / amount / select / multiselect / date / daterange / user / org / tag / boolean / file / files |
| 必填 | 不填能否提交 | 是 / 否 / 条件必填（列联动规则） |
| 长度 | 文本最大字符数（中文按字符计） | 整数 |
| 校验 | 提交时执行的校验 | 见 1.3 |
| 发起后 | 提交发起后是否可修改 | 只读 / 可改 / 仅补件（见 1.2） |
| 默认值 | 预填内容 | — |
| 联动 | 显示/必填/取值依赖的其他字段 | — |

### 1.2 字段的三态读写模型（**核心约束**）

单据存在三个生命周期阶段，字段的读写权限不同。这是防止"已审批内容被偷改"的关键机制：

| 阶段 | 可写字段 | 说明 |
| --- | --- | --- |
| **草稿** | 全部可写 | 发起人自由编辑 |
| **审批中** | 无（全部只读） | 审批人只能填意见、加签、流转、回退、请求补件，**不能改单据内容** |
| **待补件** | **所有附件类字段（`type ∈ {file, files}`）** + `补件说明`（`supplement_note`） | **主字段一律只读**；需要改主字段必须走「驳回 → 修改 → 重新提交」 |

> **「附件」指的是字段**类型**，不是字段名（2026-10 裁定）**：待补件窗口放行的是 `form_schema_json.fields[]` 里**所有 `type ∈ {file, files}` 的字段**，外加系统附件字段码 `attachments`（该码可能不在 schema 内）与补件说明 `supplement_note`。因此合同单的 `counterparty_docs`（同为附件类字段，见 §4）在待补件期**既能上传也能删除**；此前的实现把它写死成「名为 `attachments` 的字段」，导致该字段被误判为主字段（40304）。
>
> **反向约束（不得放宽）**：文本 / 金额 / 日期 / 枚举 / 选择器等**任何其它类型**的字段在待补件期**仍然只读**（40304）；**审批中**与**已完结**两个窗口的只读口径**完全不变**（附件类字段在这两个窗口同样只读）。

> **唯一例外（三态模型的边界）**：印鉴证照审批单的 `return_status`（归还状态）与 `return_date`（归还日期）**不适用上表"审批中全部只读"**——它们记录的是事后事实（证照是否已归还），属于**登记性字段**。例外规则：**草稿**可改；**审批中**仅**发起人（归还登记）**与**节点⑦归档登记人**可改，单据其余字段一律只读；**待补件期同样只读**（补件只开放附件类字段与补件说明）。完整操作人与限制见第 5 节。

> 实现要求：服务端必须按状态白名单校验可写字段，**不能仅依赖前端置灰**。见 PRD REQ-FLOW-023 与 AC-28。

### 1.3 通用校验规则

| 校验类型 | 规则 | 错误提示文案 |
| --- | --- | --- |
| 必填 | 非空（空字符串、全空格视为空） | 「请填写{标签}」 |
| 长度 | 字符数 ≤ 长度上限 | 「{标签}不能超过 {N} 个字符」 |
| 金额 | > 0，最多两位小数，≤ 99,999,999,999.99 | 「金额必须大于 0 且最多两位小数」 |
| 日期 | 不早于今天（部分字段为不早于发起日） | 「{标签}不能早于今天」 |
| 日期区间 | 结束 ≥ 开始 | 「结束日期不能早于开始日期」 |
| 文件 | 格式与大小见 1.4 | 「{标签}仅支持 {格式}，单个文件不超过 {N}MB」 |
| 条件必填 | 依赖字段满足条件时非空 | 「{标签}为必填」 |

### 1.4 附件通用限制

| 项目 | 规则 |
| --- | --- |
| 单文件大小 | ≤ 50 MB |
| 单次上传数量 | ≤ 20 个（**一次上传请求**内提交的文件数；与字段、与已有附件数无关，见 §1.4.3） |
| 单字段累计数量 | ≤ 该字段模板 `filePolicy.maxCount`（缺省 **20**）；与「单次上传数量」是两个独立口径，见 §1.4.3 |
| 单张单据附件总数 | ≤ 50 个（含补件；覆盖本单**全部**附件字段，不因模板放宽而放宽） |
| 允许格式 | `pdf` `doc` `docx` `wps` `xls` `xlsx` `ppt` `pptx` `jpg` `jpeg` `png` `heic` `zip` `rar` `7z`（**V0.4 放行 `wps` 与 `heic`**；服务端需做预览降级：`wps` 提示下载查看、`heic` 转 jpg 预览——**`heic` 转码本期未实现**，见下行） |
| 预览降级（**实现现状**） | `wps`：**不做在线预览**，提示「下载查看」（已实现）；`heic`：真源要求**转 `jpg` 后预览**，**本期未实现**（需要图像处理依赖）⇒ 预览按 MIME 白名单**降级为下载**（`Content-Disposition: attachment`，不报错、不内联渲染），**已排期阶段 3**——与电子签名一起引入图像处理依赖，避免装两次。**该缺口不得记为「已实现」**，真源口径见 `enums.md` §12.1 与 TC-FORM-033 |
| **禁止格式** | `exe` `bat` `cmd` `js` `vbs` `ps1` `dll` `msi` `scr`（上传即拒绝，服务端做**三层校验**：扩展名（黑名单优先于白名单）→ 客户端声明的 MIME → **魔数内容嗅探**，见 §1.4.1） |
| 存储 | 私有化本地存储，**不存公网**；下载必须经鉴权接口，**禁止直链**——工程不注册任何静态资源映射，存储路径没有任何 URL 可触达，直链访问得到 **404**（见 `prd-0.1.md` AC-45） |
| 文件名 | **展示名与存储名分离**：展示名剥离路径分隔符与 `..`、限长 255 并保留扩展名；存储名为服务端随机名，客户端字符串不参与路径拼接（见 §1.4.2） |
| 删除 | 仅**上传者本人 ∪ 单据发起人本人 ∪ 系统管理员**、且仅在**草稿 / 待补件**窗口内可删；实现为**先删物理文件、再删元数据行**（同事务）的**硬删**（见 §1.4.4） |
| 补件轮次 | 附件带 `round` 标记：`0` = 原始附件，`1..3` = 第 N 次补件（见 `data-model.md`） |
| `task_id` | **当前一律留空**（无可靠的「补件请求 ↔ 审批任务」关联来源，见 §1.4.5） |

> 上表的「单次上传数量」「单字段累计数量」「单张单据附件总数」**三档限额同时生效**，不是同一件事的三种说法（§1.4.3 给出区分判据）。

#### 1.4.1 附件格式的三层校验（**实现口径**，2026-10 回写）

服务端按**固定顺序**逐层判定，任一层不通过即拒绝；**批量上传先全量校验、再落盘落库**，因此「一批里第 2 个不合格」不会留下第 1 个已落盘的文件：

| 层 | 判据 | 说明 |
| --- | --- | --- |
| ① 扩展名 | 取原始文件名的小写扩展名（**无扩展名即拒**） | **`denyExt` 黑名单优先于 `allowExt` 白名单**：先命中 9 种禁止格式立即拒绝，再看是否在 15 种允许格式之内。两层清单都可由模板 `filePolicy` 收窄 |
| ② 客户端声明的 MIME | 命中危险 MIME 清单（可执行文件、脚本类的标准 MIME）即拒 | 客户端声明**不可信**，这一层**只能加严、不能放行**——不在清单里不等于通过，仍要过第 ③ 层 |
| ③ 魔数内容嗅探 | 读文件头若干字节判**内容家族**，要求「家族 ∈ 该扩展名允许的家族」 | **本层是相对 V0.4 真源的加强（只收紧、不放宽）**：真源原文只写「扩展名 + MIME 双重判断」（`enums.md` §12.2），本层在此之上再判文件头 |

**扩展名 → 允许的内容家族**：`pdf`→PDF（`%PDF-`）；`jpg`/`jpeg`→JPEG（`FF D8 FF`）；`png`→PNG；`heic`→HEIC（ISO-BMFF `ftyp` + `heic`/`heix`/`mif1`/`msf1` 等品牌）；`doc`/`xls`/`ppt`→OLE2；`docx`/`xlsx`/`pptx`/`zip`→ZIP；`wps`→OLE2 **或** ZIP；`rar`→RAR；`7z`→7-Zip。

**无条件拒绝的内容家族**（与扩展名无关）：PE/COFF 可执行体（`MZ`）、ELF（`\x7FELF`）、`#!` 开头的脚本。因此「`.png` 里塞 PE」「`.pdf` 里塞 `#!` 脚本」都会被拒。**0 字节文件**与**头字节不足、无法识别家族**的文件同样拒绝（不做「识别不出就放行」的兜底）。大小判定放在格式判定之后，以便先给出确定性更高的「格式不允许」结论。

**已知局限（如实记录，不要当成已解决的问题）**：

1. `docx` / `xlsx` / `pptx` **只按 ZIP 容器判**，**未做 OOXML 深校验**（不解压、不校验 `[Content_Types].xml` 等内部结构）；
2. 因此 **`.zip` 与 OOXML 三兄弟在内容层无法区分**（文件头都是 `PK\x03\x04`）——把 `.docx` 改名成 `.zip`（或反之）可以穿过第 ③ 层；这两类由扩展名白名单与业务用途约束兜底，而不是由内容层兜底；
3. `wps` 同时放行 OLE2 与 ZIP 两族，因而它与 `doc` / `docx` 在内容层同样无法区分。

#### 1.4.2 文件名：展示名与存储名分离（**实现口径**）

| 名称 | 落库位置 | 生成口径 |
| --- | --- | --- |
| **展示名** | `flow_attachment.file_name`（`VARCHAR(255)`） | 对客户端原始文件名安全化：`\` 与 `/` 都按路径分隔符取**末段**；剔除控制字符（`< 0x20` 与 `0x7F`）后 `trim`；剔除全部 `..` 片段并去掉前导 `.`；结果为空或只剩 `.` / `..` 时兜底为 `unnamed`；**按字符**超过 255 时**保留扩展名**、截断中段。展示名只用于界面显示与下载响应头 `Content-Disposition`（另按 RFC 5987 编码为 `filename*=UTF-8''…` 并给一个 ASCII 回退名） |
| **存储名** | `flow_attachment.storage_path` | **服务端随机生成**（32 位十六进制 + 已通过白名单的扩展名），与展示名**完全分离**；客户端字符串**不参与**任何路径拼接 |

存储布局为 `yyyy/MM/dd/<随机名>.<ext>`，落库存**相对路径**；存储根由配置项 `oa.attachment.root` 指定，缺省为 **`${user.home}/.oa/attachments`**（用户目录下、**仓库之外**），且工程不注册任何静态资源映射。目录穿越因此**在拓扑上不成立**（不靠 `..` 黑名单）：拼接并规范化后的绝对路径必须仍落在存储根**之内**且不等于存储根，否则 fail-closed。

> 例：客户端上传 `../../../etc/evil.pdf` → 展示名安全化为 `evil.pdf`、存储名为随机名，两者不同；300 字符的文件名 → 截断到 255 且保留扩展名。

#### 1.4.3 「20」的两个口径（**两个都要判，不是重复校验**）

| 口径 | 出处 | 含义 | 与另一个口径的区别 |
| --- | --- | --- | --- |
| **单次上传数量 ≤ 20** | 本表「单次上传数量」（§1.4） | **一次 HTTP 上传请求**内提交的文件数上限（多文件一次提交，按本次请求计数） | 与字段无关、与已有附件数无关；防的是「一次请求塞爆」 |
| **单字段累计 ≤ `maxCount`（缺省 20）** | `templates.md` §2.3 `filePolicy.maxCount` | **某一个附件字段**在本单据上「已有 + 本次」的**累计**上限；缺省 20 | 防的是「分多次请求绕过模板配置」。它是模板的可配置项：配正数即按该值生效（最终仍受「单张单据总数 ≤ 50」约束），配成非正数视为配置错误、按缺省 20 兜底（绝不放行成「无上限」） |

两处的缺省值**恰好都是 20**，但**判据不同、必须分别判定**——不得因为「看起来重复」而删掉其中一个：删掉单次口径则一次请求可无限塞；删掉字段累计口径则模板的 `maxCount` 形同虚设。第三档「单张单据附件总数 ≤ 50 个（含补件）」覆盖本单全部附件字段，**不受模板影响**。

#### 1.4.4 附件删除规则（**实现口径**，2026-10 回写）

**谁可以删（三档，2026-10 裁定）**

| 操作人 | 结果 |
| --- | --- |
| **上传者本人**（`flow_attachment.uploader_id` = 当前用户） | 允许（仍须通过下面的「何时可删」） |
| **单据发起人本人**（`flow_instance.initiator_id` = 当前用户） | 允许（仍须通过下面的「何时可删」） |
| **系统管理员** | 允许（仍须通过下面的「何时可删」） |
| 其他任何人（含本单其他审批人、抄送人、同部门同事） | **403**，错误码 40310「无权删除该附件：仅上传者本人、单据发起人本人或系统管理员可删除（doc/forms.md §1.4.4）」 |

> **为什么发起人本人也算「能删的人」**：单据是**发起人的**。系统管理员**代传**时（管理员 ≠ 发起人），`uploader_id` 记的是管理员；若判据只有「上传者本人」，就会出现「**发起人本人反而删不掉自己单据上的附件**」——代传只应「**多一个能删的人**」，不应让本人失去删除权。
>
> **不放宽到「任何有权看该单据的人」**：数据域内**可见** ≠ **可删**。同部门同事、本单审批人、抄送人即便能打开该单据，删除仍被 40310 拒绝（越权矩阵与可执行用例见 `test-cases.md` TC-FORM-034~038）。

**何时可删**：仅**草稿**与**待补件**两个窗口——与 §1.2 三态写白名单**同一判据**（**审批中、已完结一律不可删**，返回 **403**，错误码 40304「当前状态不允许修改字段」）。越窗删除与越窗上传**同码**，因此不存在「先删掉、再重传」的写旁路。

**一致性取舍：先删物理文件、再删元数据行（同一事务）**

| 步骤 | 失败时的后果 |
| --- | --- |
| ① 删除物理文件 | 失败 → **500**（50004 附件存储不可用）→ 事务回滚 → **元数据行保留**，用户可重试，磁盘与库仍一致 |
| ② 删除元数据行 | 失败 → 事务回滚，但文件已删 → 留下「悬挂行」，下载按 **404** fail-closed 处理（不泄露内部细节） |

**为什么不反过来（先删元数据、再删文件）**：那会产生「**无人引用却仍占空间**」的**孤儿文件**——没有任何调用方会去发现它，也没有任何报表会统计它，磁盘只增不减；而正序下最坏情况只是一条「下载即 404」的悬挂行，是**可发现、可收敛**的形态。故取正序：**文件删除失败则事务回滚、元数据保留可重试**。

**硬删，不是软删**：`flow_attachment` 没有 `deleted_at` / `status` 列（DDL 真源 `data-model.md` §6.2），因此删除 = **物理删除文件 + 删除元数据行**的**硬删**，**不得**在本层自造软删语义。若将来业务要求「删除留痕 / 可恢复」，正确路径是先走真源闭环为该表加列，而不是在应用层模拟。删除成功写审计日志（动作 `attachment_delete`）。

#### 1.4.5 `flow_attachment.task_id` 的语义（**当前一律留空**）

- DDL 真源 `data-model.md` §6.2 的列注释写「补件附件关联的请求；原始附件为空」，并有外键 `flow_attachment.task_id → flow_task(id)`。
- 但补件请求在 `flow_supplement` 中只记 **`node_instance_id`（指向 `flow_node_instance`）**，**没有 `flow_task` 的 id**；系统当前**不存在**把一条附件可靠关联到某个 `flow_task` 的来源。
- 因此实现**一律写 NULL**（原始附件与各补件轮次附件都是 NULL）：**这是有意的留空，不是漏写**，也不做「按节点或时间猜一个 `task_id`」的近似填充——错误的关联比留空更糟（会把附件挂到错误的审批任务上）。
- 轮次信息由 `flow_attachment.round` 承载（`0` = 原始附件、`1..3` = 第 N 次补件，见 `enums.md` §12.3），与 `task_id` 无关。
- 结论：`task_id` 当前是**保留列**。若将来需要「按审批任务检索附件」，应先在真源中补齐「补件请求 ↔ 任务」的关联，再回填本列。

### 1.5 金额字段的统一规则（全局）

| 规则 | 说明 |
| --- | --- |
| 存储 | 以 `DECIMAL(18,2)` 存储，**不使用浮点数** |

## 9. 实单字段的处置决定（Q8–Q10 已关闭）

对照 `doc/参考文档/` 的三张纸质实单后，发现实单要求填写、但系统原设计没有对应的字段。**业务已确认如下处置，三项问题均已关闭，不再是"待确认"**：

| 编号 | 字段 | 处置决定 | 对系统的影响 |
| --- | --- | --- | --- |
| **Q8** | **计划类别**（计划内 / 计划外） | **✅ 已关闭**——纳入字段，实现为**布尔 checkbox**（勾选＝计划内），一期只存储数据，不参与任何流程判断；待二期「计划管理」模块上线后再启用其业务含义 | 表单新增布尔 checkbox 字段，**不入 `dict_type`**；一期流程引擎**不得**引用该字段做路由 |
| **Q9** | **付款归属**（本月度 / 本年度 / 以前年度） | **✅ 已关闭**——同上，实现为**布尔 checkbox**（勾选＝本月度，**默认勾选**），一期只存储数据 | 表单新增布尔 checkbox 字段，带默认值，**不入 `dict_type`** |
| **Q10** | **事项分类增加「投资」** | **✅ 已关闭**——作为配置项纳入（**五类**）；由管理后台在数据字典中维护；五个类别统一归属财务部（财务管理），不做细分 | 见下方「路由模型简化」——**类别不再决定归口部门，也不参与路由** |

### 9.1 路由模型简化（Q10 的连带结论）

原设计（PRD 6.1、5.3）按「事项类别 → 归口部门」做一对一路由映射：

```
经营→经发部 · 经济→财务部 · 行政→集团办 · 人力→人力资源部
```

**业务确认：五个类别（含新增的「投资」）统一归属财务管理，不再细分。**

这意味着：

| 项目 | 原设计 | 确认后 |
| --- | --- | --- |
| 集团归口部门 | 按类别路由到 4 个不同部门 | **恒为财务部**（财务管理） |
| 路由判据 | 事项类别决定归口部门 | 类别**不再决定归口部门**，仅作为分类标签与统计维度 |
| 数据域（PRD 5.3「集团职能部门只看本部门归口类别」） | 财务部只看经济类 | 该限制对财务部**不再适用**（它本就该看全部类别的资金事项） |
| 事项类别的取值 | 4 个固定值（无「投资」） | **改为配置项**（数据字典），**五类**（含新增「投资」），可增删 |
| 一期是否仍需「路由」 | 需要（4 条分支） | **不需要**——主干唯一的"分支"变成「是否涉及费用」（事项审批单） |

> **重要**：这不改变「全部单据无条件上集团」的结论，只是把"上集团后由谁接"从"按类别分流"简化为"统一财务"。**链路结构不变，只是归口节点的人变了。**

### 9.2 归口节点的合并结论（Q11 + Q12 均已确认）

路由统一到财务部后暴露出"财务部会不会连审两次、分公司与集团是否各审一次"的问题。**业务已确认：两处都合并。**

| 编号 | 问题 | 结论 |
| --- | --- | --- |
| **Q11** | 原「集团归口部门」节点与「财务部复核」是否同一件事？ | ✅ **已确认：同一件事，合并为一个节点**。该节点**既是费用复核、也是集团归口部门审批**，财务部**只审一次**；集团层不再有独立的归口部门节点 |
| **Q12** | 原分公司层「归口部门负责人」（②）是否也与③合并？ | ✅ **已确认：合并**。分公司的独立财务节点取消，归口职责全部由**集团财务部**一个节点承担 |

**合并后的最终主干（7 个审批节点）**：

```
① 直属部门负责人
→ ② 财务部复核【= 集团归口部门，只审一次】
→ ③ 分公司分管领导
→ ④ 子公司总经理
→ ⑤ 集团分管领导
→ ⑥ 集团董事长
→ ⑦ 归档登记（集团处理部门流转）
→ 结束
```

> **节点口径（V0.4 统一）**：主干为 **7 个审批节点**（①–⑦，编号即为审批节点序号）。旧稿的"8 个节点""9 个节点"表述**一律废弃**——那是把「发起者」或「结束」也计入节点数造成的误记；**发起者与结束不是审批节点**。旧的"按类别路由到 4 个部门""归口部门独立节点"表述同样废弃。

> **协同审批不占主链编号**：由②的审批人在审批时勾选协同/会签部门，作为②节点下的**并行子任务组**，全部完成后继续至③。

**三条必须写进实现的细则**：

1. **撤回边界随之前移**：原「节点⑥通过前可撤回」→ 现为「**节点②（财务部复核）通过前可撤回**」（PRD 6.4 REQ-FLOW-009 / AC-16 已同步）。
2. **"不涉及费用"时跳过②，但归口部门仍记为财务部**：事项审批单选「不涉及费用」时，②的状态为「已跳过」、不产生待办；但**单据的归口部门字段仍记录为财务部**，用于统计与审计（否则报表里会出现"无归口部门"的单据）。
3. **分公司财务不再单独把守**：若业务上确实需要"分公司财务先看一遍"，必须在**②节点下配置协同/会签**，不得再新增独立节点（否则与 Q12 的合并结论冲突）。

### 9.3 一期不做的事（避免误解）

- **不做**资金计划模块：Q8「计划类别」在一期只是一个被记录的勾选项，**没有计划编制、没有计划与实际的比对、没有超计划拦截**。
- **不做**账龄与预算执行率报表：Q9「付款归属」同理，一期只存不分析。
- **不做**投资类支出的专项流程：Q10 的「投资」与其他四类走**完全相同的流程**，无任何特殊节点。

| 附件清单 | 打印稿附「附件清单」区，列出文件名（不含文件本体），补件附件标注轮次 |
| 分页 | **常规数据量下每张单据恰好一页**；当明细行或流转段落**超出 A4 可容纳行数**（正文 9.5pt / 行高 1.42 时约 55 行）时**按行分页**，每页保留表头（`thead` 重复），页脚标注「**第 X / Y 页**」。详见下节 |

### 10.1 打印版式映射（四类单据 × 集团/子公司层）

**版式按"单据在集团层还是子公司层办理"选择，其中事项审批单是唯一的统一例外**：

| 单据 | 集团层（发起人属集团本部） | 子公司层（发起人属子公司） | 依据 |
| --- | --- | --- | --- |

### 10.2 分页与超长内容的处理

| 情形 | 处理 |
| --- | --- |
| 常规数据量 | **每张单据恰好一页**（实测见 DESIGN.md「实测页面高度」：274 / 242 / 270 / 205 mm，均 ≤ 297mm） |

## 11. 表单模板实现要求

1. **字段定义驱动渲染**：表单由 `flow_template.form_schema_json` 驱动，不在前端硬编码字段（四类单据共用一套渲染器）。
2. **服务端二次校验**：所有必填、长度、金额、日期校验必须在服务端执行，前端校验仅为体验。
3. **字段级权限**：金额与账号类字段按角色脱敏/隐藏，规则见 PRD 5.3。
4. **快照**：单据提交时把 `form_schema_json` 的版本号与 `fields_json` 一并固化，模板后续变更不影响在途单据。
5. **金额字段禁止浮点**：服务端只接受字符串或定点数，禁止经过浮点运算后再落库。
6. **变更流程**：新增字段 → 更新本文档并升版本 → 在后台新增模板版本 → 已发起单据不受影响（PRD REQ-FLOW-006）。

7. **打印标签可配置**：每个字段带 `printLabel` / `printVisible`，打印稿按此渲染（见第 10 节）。
