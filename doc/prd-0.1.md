## 第2章 项目背景与目标

### 2.1 项目背景

- 集团主要业务覆盖**供热、贸易、医疗**行业，员工人数300+。
- 集团采用多公司架构，包含集团总部及多家子公司，组织层级为**集团-公司-部门-科室**四级。
- 目前无OA/ERP系统，审批流程全部线下流转，存在效率低、过程难追溯、权限不清晰等问题。
- 集团急需统一审批入口，实现跨公司、跨部门的线上协同审批。

### 2.2 项目目标

- 搭建集团统一OA审批平台，覆盖集团总部及所有子公司。
- 实现事项审批单、资金审批单、合同审批单、印鉴证照审批单四类核心审批单的线上流转。
- 建立多公司权限隔离机制：子公司数据隔离，集团职能部门数据互通。
- 支持H5移动端审批，浏览器直接访问，保持登录状态。
- 支持审批节点电子签名，手写签名可预存并快捷调用。
- 满足基础安全合规（非严格等保），私有化本地部署。
- 预留后续经营决策、人力资源、计划管理、合同管理系统集成能力。

### 2.3 成功指标（建议）

| 指标                     | 目标值            | 说明 |
| ------------------------ | ----------------- | ---- |
| 审批流程线上化率         | 100%              | 四类单据全部线上流转，不再保留线下签字路径 |
| 平均审批耗时             | 较线下缩短50%以上 | 口径：发起→终审通过（排除发起人撤回与驳回重提） |
| 用户活跃度               | 月活用户占比≥80%  | 月内至少登录并处理过1次待办 |
| 移动端可审批（**功能约束，非占比指标**） | 四类单据均可在手机浏览器完成审批与签名 | 一期不对接企业微信/钉钉、**无推送通道**（通知渠道见 6.7），移动端审批量取决于用户自觉，故不设占比目标 |
| 系统可用性               | ≥99.5%            | 按工作日 8:00–20:00 计算 |

> **指标口径说明**：一期所有指标以「系统内可查」为准，报表能力见 REQ-ADMIN-005（**P1 ＝ 第四阶段**，见第 11 章）。

- 消息通知（站内信、邮件、抄送；一期无移动端推送）
- 附件管理（REQ-FORM-002：格式/大小/数量白名单、私有化存储与鉴权下载）

- 条件路由与金额分级审批——一期流程为线性主干，**金额与事项类别均不参与路由**（见 6.1；金额档位见附录 D Q2）
- 按发起时快照解析审批人之外的动态改派——调岗/离职不改动在途单据（见 5.5）

## 第5章 组织架构与权限模型

### 5.1 组织架构模型（REQ-ORG-001）

系统采用**集团-公司-部门-科室**四级架构，支持多公司、多层级动态扩展。

- **组织节点字段**：名称、类型、上级节点、负责人、状态（启用/停用）。
- **负责人绑定**：
  - 每个部门/科室可指定一个或多个负责人（支持一人多岗）。
  - 集团层指定“分管领导”，按业务线绑定（如：财务分管领导、人力分管领导、行政分管领导、经营分管领导）。
- **人员归属**：一名员工可同时挂职于多个组织节点。
- **集团职能部门**：经发部、财务部、人力资源部、集团办。**审批归口统一由财务部承担**（五个事项分类不细分）；其余部门作为协同/会审部门参与（支持跨公司查看对应数据）。

**示例结构**：

集团
├── 公司A
│ ├── 部门1
│ │ ├── 科室1-1
│ │ └── 科室1-2
│ └── 部门2
├── 公司B
└── 集团职能部门
├── 经发部（负责人：张三）
├── 财务部（负责人：李四）
├── 人力资源部（负责人：王五）
└── 集团办（负责人：赵六）

### 5.2 权限模型（REQ-AUTH-001 数据隔离、REQ-AUTH-002 越权拒绝）

采用 RBAC + 数据域双层模型。

- **子公司数据隔离**：子公司员工及负责人仅能查看本公司数据，不可跨公司访问。
- **集团职能部门互通**：集团经发部、财务部、人力资源部、集团办可跨公司查看对应数据（口径见 5.3）。**审批归口统一为财务部**——财务部可见**其归口类别（资金/合同/印鉴证照，以及与所有「涉及费用」的事项审批单）**，并可见**流转链承接或经过财务部的单据**；**不涉及费用且未经流转的事项单财务部不可见**（V0.4 裁定，见 5.3 与附录 D Q13）。其余部门按其协同/会审参与范围可见。
- **权限树配置**：IT部门在后台为每个角色勾选可访问的组织节点和功能菜单，支持逐级分配。
- **分公司流程管理员**：由IT部门分配，可配置本公司流程模板、维护本公司组织与人员、查看本公司数据，**不可再向下分配权限**，不可跨公司操作。
- **权限变更留痕**：任何角色、数据域、权限树勾选的变更都必须写入审计日志（操作人、时间、变更前后值），见 REQ-LOG-004。

### 5.3 数据域口径（可验收定义；REQ-AUTH-003 字段级限制、REQ-AUTH-004 流转可见性）

「对应归口数据」不能只写形容词，一期按下列口径执行：

| 角色 | 可见数据范围 | 判定依据 |
| --- | --- | --- |
| 普通员工 | 本人发起的单据 + 本人作为审批人/抄送人的单据 | 发起人 / 任务 assignee / 抄送人 |
| 部门/科室负责人 | 本部门/科室成员发起的单据 + 本人审批的单据 | 发起人所属组织节点 ∈ 本部门/科室 |
| 子公司总经理 | 本公司的**全部**单据 | 发起人所属公司 = 本公司 |
| 分公司流程管理员 | 本公司的全部单据 + 本公司流程模板 | 同上 |
| 集团职能部门（**财务部**） | ① 全部**资金/合同/印鉴证照**类单据（归口类别，恒经节点②）；② 事项审批单中「涉及费用＝是」者（经节点②）；③ 流转链承接或经过财务部的单据（任意类别）；④ 本部门在途单据。**「不涉及费用」且未经流转的事项审批单不可见** | 归口类别 ＝ 资金/合同/印鉴；事项单看 `involve_cost` 与 `flow_routing`；V0.4 裁定见附录 D Q13 |
| 集团分管领导 | 全集团范围内、**与本业务线相关**的全部单据 | 单据经过本人所在业务线节点，或事项类别属于本人分管类别 |
| 集团董事长 | 全集团全部单据 | 无过滤 |
| 系统管理员（IT部门） | 全集团全部单据 + 全部配置 | 无过滤 |

**流转可见性（与 6.3.1 配套，必须实现）**：

当单据在集团层被流转给其他部门时（见 6.3.1），**流转链上的部门负责人对这张在途单据必须可见**，即便该单据的事项类别不属于其归口类别。判定依据：

- 该用户的 org 出现在单据 `flow_instance` 的**流转链记录**中（即被指定为流转目标部门）；
- 可见范围**仅限该张单据**，不得因此放宽该部门对同类其他单据的可见性（避免"财务部因为被流转过一次，就永久看到全部经营类单据"）；
- 单据完结后，流转链部门的可见性**保留**（历史可查），但不再获得新的单据。

**字段级限制（一期）**：

- 单据正文与附件对所有可见该单据的角色开放；
- **合同金额、资金金额**对非财务类角色只读展示，不可导出；**导出功能仅系统管理员与财务角色可用**，导出行为写入审计日志；
- 员工**手机号**在通讯录中默认脱敏（`138****8888`），仅本人与系统管理员可见完整值。

> 说明：一期不做字段级白名单配置，上表为硬编码规则。若后续出现"同一单据内不同字段不同可见范围"的需求，再升级为字段级权限模型（列为 P2）。

### 5.4 审批人解析与节点决议规则

**解析时机**：审批人在**流程发起时一次性解析并固化**为快照（REQ-FLOW-011）。此后发生调岗、离职、组织调整、负责人变更，**在途单据一律不变**，仍由快照中的审批人处理；如确需换人，由审批人使用「转办」（见 6.6）或由系统管理员在审计留痕下改派。

**解析规则表**：

| 节点 | 解析规则 | 输出 |
| --- | --- | --- |
| 直属部门负责人 | 取发起者所在科室的负责人；科室未设负责人时上溯取所属部门负责人 | 候选人集合 |
| 财务部复核（② **= 集团归口部门**） | **恒取集团财务部负责人**（五个事项分类统一归口财务，不细分）；该节点同时承担费用复核与集团归口审批，**只审一次**（Q11+Q12） | 候选人集合 |
| 分公司分管领导 | 按发起者所属公司匹配分公司绑定的分管领导 | 候选人集合 |
| 子公司总经理 | 取发起者所属公司的总经理 | 候选人集合 |
| 协同部门（②的并行子任务） | 由②的审批人**在审批时勾选**，每个被勾选部门取该部门负责人 | 候选人多组（每组独立会签） |
| 集团分管领导 | 按事项类别匹配集团层绑定的分管领导 | 候选人集合 |
| 集团董事长 | 取集团董事长 | 候选人集合 |
| 指定人员/角色 | IT部门在流程设计器中固定指定 | 候选人集合 |
| 发起人自选 | 发起时由发起人从通讯录中选择 | 候选人集合 |

**节点决议模式**（每个节点可独立配置，REQ-FLOW-002）：

| 模式 | 通过条件 | 默认 |
| --- | --- | --- |
| 或签 | 候选人中**任意一人**通过即节点通过；其余人的任务自动关闭 | ✅ 默认 |
| 会签 | 候选人中同意人数达到配置的**通过阈值**（百分比或绝对人数，如 2/3 或过半）后节点通过；任一人驳回则节点驳回 | |
| 依次审批 | 候选人按配置顺序**串行**审批，全部通过才通过；任一人驳回则节点驳回 | |

**配置约束**：

- 通过阈值支持「百分比」（如 66%）与「绝对人数」（如 2 人）两种写法，二者同时存在时以绝对人数优先；
- **驳回后的去向一期固定为「回到发起人」**，不做节点级配置（见 6.6）；会签或协同任务中任一人驳回，即该节点驳回；
- 候选人集合为空（如部门未设负责人、总经理离职未补）时，**禁止发起**并提示「XX 节点无有效审批人，请联系管理员配置」，不允许静默跳过——静默跳过会让单据绕过审批，属于严重内控缺陷；
- 同一人在同一节点出现多次时自动去重；
- 同一人同时是多个串行节点的审批人时，默认**逐节点分别审批**（不做连续节点自动合并），如需合并由流程设计器显式配置。

### 5.5 组织与人员变更的处理（REQ-ORG-002 离职/停用前的补偿控制）

| 场景 | 一期处理方式 |
| --- | --- |
| 审批人调岗/离职 | 在途单据不改派，仍由快照审批人处理；无法处理时由系统管理员在留痕下改派，或由该节点其他候选人（或签/会签）完成 |
| 负责人空缺 | 发起时即拦截（候选人集合为空的校验） |
| 组织节点停用 | 停用前必须处理完该节点全部在途单据；停用后不可作为发起者的归属节点。**唯一例外见下方强制继续** |
| 员工离职 | 离职前必须处理完名下全部待办；系统提示未处理任务数量，强制要求先转办或改派。**唯一例外见下方强制继续** |
| 批量调整（如公司重组） | 由系统管理员导入；导入前系统给出受影响在途单据清单，确认后方可执行 |

> 上述「离职前必须处理完待办」与「停用前必须处理完在途」是一期采用快照策略的**必要补偿控制**——否则快照会导致单据永久卡死。这两条都列入验收（AC-11、AC-12）。

> **强制继续（唯一例外，2026-10-02 业务裁定）**：当在途/待办非零时，系统**默认阻断**；但**系统管理员**可在影响清单上勾选「强制继续」并**必填原因**后放行（适用于人员失联、突发重组等无法先清空的场景）。
> 约束：① 仅系统管理员可用（普通管理员/分公司管理员不可）；② 原因必填（≤500 字），缺失则 400；③ **双留痕**——审计日志 `sys_log` 记录操作人、对象、在途/待办数量、原因与 `force=true`，运行日志同步 `log.warn`；④ 阻断默认行为不变：未显式勾选强制继续时一律拒绝。
> 该例外适用于：组织节点停用、员工离职、以及后台把人员状态改为「停用」（三者共用在途/待办检查）。
> 对应实现：`oa.identity.block-on-inflight`（默认 `true`）+ `ForceReasonPolicy`（准入校验）+ `InFlightGuard`（放行语义）。

## 第6章 核心功能需求

### 6.1 一期路由原则（重要）

一期**没有条件分支**。全部单据、全部金额，都走**同一条线性主干**。

由此确定四条约束：

| 约束 | 说明 |
| --- | --- |
| 金额不参与路由 | 金额仅作为单据字段记录与展示，不影响流程走向。所有金额档位判断延后到二期（见附录 D Q2） |
| 无「集团层级判断」节点 | 全部单据无条件上集团，因此原流程中的「对应集团部门判断」与「是否上集团」合并为一步 |
| **集团归口部门恒为财务部** | 五个事项类别（经营/经济/行政/人力/**投资**）**统一归属财务管理，不细分**。因此类别**不再决定归口部门**，集团归口节点恒为财务部 |
| **事项类别是配置项，仅作分类标签** | 类别取值由管理后台数据字典维护（可增删）；发起人选定后**任何节点不可改判**；类别用于统计、检索与展示，**不参与路由** |
| 计划属性只存不用 | 资金单的「计划类别」「付款归属」一期仅存储数据，**不参与任何流程判断**（详见表单字段字典） |

> **与 V0.3 早期的差异**：原设计为"经营→经发部、经济→财务部、行政→集团办、人力→人力资源部"的按类别分流。业务已确认**统一归财务**，故该判据取消。**链路结构不变，只是归口节点的人从"四个部门"变为"财务部一个"。**

一期的"分支"只剩一处：事项审批单的「**是否涉及费用**」——决定是否跳过财务部复核节点（见 6.3 节点②）。

### 6.2 四类审批单与事项类别的关系

四类单据共用同一套审批引擎与同一条主干，通过「表单模板 + 流程模板」组合区分。**五类事项分类统一归口财务部，不细分为不同部门。**

| 单据类型 | 事项类别（默认值） | 与主干的差异 |
| --- | --- | --- |
| **事项审批单** | 发起人选择（配置项，含经营/经济/行政/人力/投资） | 无差异，走完整主干；**唯一带"是否涉及费用"判断的单据** |
| **资金审批单** | 默认「经济」 | 金额必填；新增「计划类别」「付款归属」两个**只存不用**字段；附件必填 |
| **合同审批单** | 默认「经营」 | 归口仍为财务部；须上传合同文本附件 |
| **印鉴证照审批单** | 默认「行政」 | 归口仍为财务部；须填写使用期限与归还状态 |

> **与 V0.3 早期的差异**：原设计按类别分流到经发部/财务部/集团办/人力资源部。业务确认**统一归财务部**后，四类单据的归口节点完全相同，差别只在**字段与校验**（金额、附件、专用字段），不再有路由差别。

**打印要求**（REQ-FORM-001）：四类单据均须支持**打印为 A4 纸质单据**，版式与集团现行纸质实单一致。**版式映射（V0.4 定稿）**：

| 单据类型 | 集团层 | 子公司层 |
| --- | --- | --- |
| 事项审批单 | **子公司内部审批单版式（统一）** | 子公司内部审批单版式 |
| 资金审批单 | 集团「资金审批单」版式 | 子公司内部审批单版式 |
| 合同审批单 | 集团「集团合同类文件流转审批单」版式 | 子公司内部审批单版式 |
| 印鉴证照审批单 | 「印鉴证照使用审批单」版式 | 「印鉴证照使用审批单」版式 |

打印稿不使用屏幕端的界面样式（无色块、无圆角、无投影），黑白复印后信息不得丢失；**签名栏一律为空栏**（供手签，屏幕预览可显示已签缩略图与时间戳）；常规数据量下**每张单据恰好一页**，明细行或流转段落超出 A4 可容纳行数时按行分页并在页脚标注"第 X / Y 页"。版式规格见 [`DESIGN.md`](../DESIGN.md)「打印规格」，样张见 [`DESIGN.print-a4.html`](../DESIGN.print-a4.html)，验收见 AC-31、AC-32。

### 6.3 主干审批链（V0.4 定稿，**REQ-FLOW-025 主干审批链定义**）

审批链以**流程草图**为准（分公司阶段在前，集团阶段在后）。

**Q11 已确认：原「财务部复核」（③）与原「集团归口部门」（③）是同一件事，合并为一个节点——财务部只审一次。**
**Q12 已确认：原分公司层「归口部门负责人」（②）与「财务部复核」（③）同样合并。最终由财务部一个节点完成费用复核与集团归口审批，主干为 7 个审批节点（①~⑦）。**

```
发起者
  → ① 直属部门负责人
  → ② 财务部复核【= 集团归口部门，同一节点】
        是否涉及费用？涉及→财务部审批；不涉及→跳过本节点
  → ③ 分公司分管领导
  → ④ 子公司总经理
  → ⑤ 集团分管领导
  → ⑥ 集团董事长
  → ⑦ 集团处理部门流转（归档登记）
  → 结束
```

> **并行协同审批的位置**：由②的审批人在审批时勾选协同部门（如需要同级部门协助）。协同任务**不占主链编号**，作为②节点下的并行子任务组，全部完成后流程继续至③。

**关键说明**：

- **②（财务部复核）是唯一承担集团归口职责的节点**：它同时是"费用复核"与"集团归口部门审批"——**同一件事，只审一次**（Q11 + Q12 确认）。因此**集团层与分公司层都不再有独立的归口部门节点**。
- **归口统一由集团财务部承担**：原设计的分公司财务口径节点已取消（Q12）。若业务上需要"分公司财务先看一遍"，应作为**协同/会签**挂在本节点上，而不是新增独立节点。
- ②由表单字段「是否涉及费用」决定（仅事项审批单会出现"不涉及"的情况；资金、合同、印鉴三类单据恒为"涉及"）。
- **集团归口部门仍记录为「财务部」**：即使事项审批单"不涉及费用"跳过②，单据的归口部门字段仍记为财务部（用于统计与审计），只是该节点状态为「已跳过」。
- ⑥的协同部门由②的审批人在审批时勾选（作为②的并行子任务）；若未勾选，②通过后直接进入③。
- ⑦为归档登记节点，由财务部内勤角色完成（可配置为"仅登记不审批"）。

#### 6.3.1 集团层流转机制（已确认：链式流转 + 回退 + 补充材料）

业务确认的规则为「**集团层面的流转由接手的第一个部门决定，根据部门选择流转到对应部门**」，并在此基础上要求：**审批节点可要求发起者补充文件**。

因此，②及之后集团层节点的审批人，在审批时可选择以下动作：

| 动作 | 需求编号 | 效果 | 制约条件 |
| --- | --- | --- | --- |
| **通过** | REQ-FLOW-001 | 节点通过，流程继续 | — |
| **驳回（退回发起人）** | REQ-FLOW-014 | 单据回到发起人修改，状态「已驳回」；重新提交后**从①重走** | 必须填写意见（≥5字） |
| **流转** | REQ-FLOW-020 | 指定**下一个部门**接手，单据继续在集团层走（支持连续流转 A→B→C） | ① 全单流转+回退总次数 ≤5；② **禁止回流到已处理过的部门**（A→B→A 拒绝）；③ 必须选择承接部门并填写流转原因；④ 承接部门对本案可见（见 5.3 流转可见性） |
| **回退上一节点** | REQ-FLOW-021 | 退回**上一个已完成的节点**重审；上一节点通过后自动回到本节点 | ① 同一节点最多被回退 2 次；② 必须填写原因；③ 计入总次数 ≤5 |
| **回到本部门** | REQ-FLOW-022 | 把后续流转收束回本部门，由本部门决定下一步 | ① 同一部门连续「回到本部门」≤2 次；② 不计入总次数但计入审计日志 |
| **要求补充材料** | REQ-FLOW-023 | 单据进入「**待补件**」子状态暂停，仅发起人可补充；补件提交后**直接回到请求补件的节点**继续 | ① 同一节点最多请求 1 次；② 全单补件 ≤3 次；③ 补件**不算驳回**（不写驳回记录、不计入驳回率）；③ 补件时限默认 3 个工作日，超时自动催办 |
| **终止** | REQ-FLOW-010 | 终态，不可再提交 | 仅系统管理员与集团分管领导；必须填写原因 |

**补充材料的边界（必须实现，否则会出现"补件时偷改内容"）**：

- 补件**只开放附件与备注**字段；**金额、对方主体、事项类别等已审批的主字段一律只读**——若发起人确实需要改主字段，只能走「驳回 → 修改 → 重新提交」，从①重走；
- 补件提交后回到**原节点**，不回到①；原节点的审批人可看到"第 N 次补件"标记与新增附件；
- 补件期间单据对异常角色（其他部门、抄送人）仍可见只读，但**不可审批**，避免出现"待补件的单据被人审掉"；
- 补件次数用尽（3 次）后，审批人只能选择通过、驳回或终止。

**流转链的两道闸**：

1. **总次数上限 5**（流转 + 回退合计），达到上限后系统拒绝继续流转/回退，并提示改用「驳回」或「终止」；
2. **禁止回流**：已处理过的部门不可再次被指定为流转目标（「回到本部门」是唯一例外，且限连续 2 次）。

> 提示：链式流转属于**一期新增的引擎能力**（见 6.4 REQ-FLOW-020），排期已计入第二阶段 8 周；若后续发现业务上很少用连续流转，可降级为"一次只转一个部门"，但规则表保留。

### 6.5 电子签名与身份确认

- **手写签名**（REQ-SIGN-001）：审批人在 H5 端点击「签名确认」后弹出签名面板，支持手写；桌面端支持鼠标书写或调用已预存签名。
- **签名预存**（REQ-SIGN-002）：用户可在个人中心预存签名图片（上传或手写后保存），审批时一键调用；预存签名可修改，修改留痕。
- **节点配置**（REQ-SIGN-003）：流程设计器中可配置每个节点「强制签名 / 可选签名 / 不签名」。默认：集团分管领导、集团董事长节点**强制签名**，其余节点可选。
- **签名记录**（REQ-SIGN-004）：签名图片、时间戳、审批人 ID、设备指纹（或浏览器指纹）、IP 与审批单**绑定存储**，写入后不可修改、不可删除，仅可重新签署并保留历史版本（见 REQ-LOG-003）。
- **签名合法性说明**：一期手写签名为**内部管理凭证**，用于留痕与责任认定，不具备《电子签名法》要求的可靠电子签名效力（无第三方 CA）。
- **为后期合法化预留**（REQ-SIGN-005）：签名记录一期即按"可升级为可靠电子签名"的形态设计，预留以下能力，一期不实现但字段与协议位不可省略：
  - 签名类型区分 `手写 / CA 数字签名`（`sign_type`）；
  - 预留 CA 签名字段：签名值、证书序列号、证书颁发者、可信时间戳来源（`ca_signature` / `ca_cert_serial` / `ca_issuer` / `tsa_source`）；
  - 预留验签结果字段（`verify_result`、`verified_at`），用于记录"该签名在何时被验证为有效/失效"；
  - 签名记录的哈希（`hash`）计算范围必须**包含上述预留字段**，接入 CA 后无需重建历史签名；
  - 签名记录**只追加**：重新签署产生新记录并保留旧记录，不覆盖、不删除。
  - 若二期引入第三方 CA，仅需新增"CA 签署/验签"交互，不改动数据模型与审计链路。

### 6.6 异常路径（一期必须实现）

V0.2 只有"快乐路径"，以下为一期必须定义的异常规则。表中「回到发起人」指单据回到草稿并由发起人修改后重新提交（**重新提交会重新解析审批人快照**）。

| 场景 | 规则 | 需求编号 |
| --- | --- | --- |
| 驳回 | 审批人驳回必须填写意见（≥5字，不允许空白驳回） | REQ-FLOW-013 |
| 驳回后去向 | **回到发起人**（固定策略，不给审批人选择权）。单据状态变为「已驳回」，发起人可修改后重新提交，或终止 | REQ-FLOW-014 |
| 会签节点的驳回 | 会签节点中任一人驳回 → 该节点立即驳回 → 单据回到发起人，其余未处理任务自动关闭 | REQ-FLOW-015 |
| 协同部门驳回 | 任一协同部门驳回 → 单据回到发起人，其余协同任务自动关闭 | REQ-FLOW-016 |
| 撤回 | 仅发起人可撤回，且仅限财务部复核节点（节点②）通过前；撤回后回到草稿，可修改重提 | REQ-FLOW-009 |
| 重新提交 | 重新提交时**重新解析审批人快照**与流程版本（按最新模板），已审过的节点不保留 | REQ-FLOW-017 |
| 转办 | 审批人可将本人任务转办给他人（含跨公司）；须填写转办原因；转办对象必须是**同一数据域内可见该单据**的人；转办后原审批人失去该任务，转办记录入轨迹 | REQ-FLOW-018 |
| 改派 | 仅系统管理员可改派（用于人员离职、快照审批人不可用）；必须填写原因并留痕 | REQ-FLOW-019 |
| 加签 | 前加签/后加签见 6.4；加签人对结果负责，加签链记入审计日志 | REQ-FLOW-003 |
| 终止 | 系统管理员与集团分管领导可终止，须填写原因；终止后单据不可再提交 | REQ-FLOW-010 |
| 超时 | 超时仅催办（站内信 + 邮件，可抄送上级），**不自动跳过、不自动升级** | REQ-FLOW-007 |
| 流转 | 集团层审批人可指定下一承接部门，连续流转；禁止回流已处理部门，总次数 ≤5（见 6.3.1） | REQ-FLOW-020 / REQ-FLOW-024 |
| 回退上一节点 | 退回上一已完成节点重审，同一节点最多被回退 2 次，必须填原因 | REQ-FLOW-021 |
| 回到本部门 | 后续流转收束回本部门，同一部门连续 ≤2 次 | REQ-FLOW-022 |
| 补充材料 | 单据进入「**待补件**」暂停，仅发起人可补附件与备注（主字段只读）；补完回到请求节点；**不算驳回**；同节点 ≤1 次、全单 ≤3 次；默认时限 3 个工作日 | REQ-FLOW-023 |
| 待补件期间 | 单据对其他角色保持只读可见但**不可审批**；补件超时仅催办发起人，不自动驳回 | REQ-FLOW-023 |

- **浏览器兼容**（REQ-USER-005）：Chrome、Edge、Safari 主流版本；**明确不支持**微信内置浏览器作为验收目标（因不走企业微信入口），但在微信中打开时须保证基本可用（不崩溃、可登录、可审批）。
- **实现约束（不在 PRD 正文约束）**：登录态的具体实现方式（Token 类型与有效期参数）由技术方案决定，PRD 只约束上述**用户可感知的行为**。

### 7.2 状态机

**流程实例状态**（见附录B）：

```
草稿 ──提交──> 审批中 ──全部节点通过──> 已通过
  ^              │  ↑
  │              │  └──补件完成（回到请求补件的节点）──┐
  │              ├──任一节点要求补充材料──> 审批中/待补件（子状态）─┘
  │              ├──任一节点驳回──> 已驳回 ──发起人修改重提──> 审批中（重新解析快照）
  │              ├──发起人撤回（节点②通过前）──> 已撤回 ──> 草稿
  │              └──管理员/集团分管领导终止──> 已终止（终态，不可再提交）
  └── 已撤回 / 已驳回 可回到草稿
```

> 「待补件」是**子状态**（`flow_instance.sub_status`），实例主状态仍为「审批中」——因为单据并未被驳回，流程只是暂停等待发起人补件。这样处理的好处是：驳回率、审批时长等统计口径不会被补件污染。

**节点实例状态**：未开始 → 进行中 → **等待补件** → 已通过 / 已驳回 / 已跳过 / **已退回** / 已取消

**任务状态**：待处理 → 已同意 / 已拒绝 / 已转办 / 已改派 / 已加签 / **已流转** / **已回退** / **已请求补件** / 已自动关闭（同节点他人已决议或单据已驳回）

**联动规则（必须实现，否则会出现挂单）**：

| 触发 | 联动结果 |
| --- | --- |
| 任一节点实例驳回 | 实例 → 已驳回；同节点其余任务 → 已自动关闭；其余节点实例 → 已取消 |
| 会签节点达到通过阈值 | 节点实例 → 已通过；该节点未处理任务 → 已自动关闭；实例推进到下一节点 |
| 或签节点任一人通过 | 节点实例 → 已通过；其余任务 → 已自动关闭 |
| 实例状态变为终态（通过/驳回/撤回/终止） | 全部进行中节点实例与任务 → 已取消 / 已自动关闭；站内信通知发起人 |
| 财务节点因"不涉及费用"跳过 | 节点实例 → 已跳过（不入审批轨迹的正经节点，仅在轨迹中留"本单不涉及费用，财务节点已跳过"记录） |
| 审批人请求补充材料 | 实例 `sub_status` → 待补件；当前节点实例 → 等待补件；该节点任务 → 已请求补件（不可再审批）；站内信 + 邮件通知发起人；`flow_supplement` 新增记录并写入 deadline |
| 发起人提交补件 | 实例 `sub_status` → 空；`flow_supplement.status` → 已补件；`supplement_count` +1；节点实例 → 进行中，任务重新回到**请求补件的审批人**；新增附件 `round` = 本次补件轮次 |
| 补件超时未提交 | 仅催办发起人（站内信 + 邮件）；**不自动驳回、不自动通过**；`flow_supplement.status` → 已超时 |
| 审批人发起流转 | `flow_routing` 新增记录（action_type=流转）；`routing_seq`/`routing_count` +1；当前节点实例 → 已通过；新承接部门的负责人产生新任务 |
| 审批人回退上一节点 | 当前节点实例 → 已退回；上一节点实例 → 进行中（`returned_count` +1）；`routing_count` +1；上一节点通过后自动回到本节点 |
| 流转/回退达到上限（**已满 5 次**）或回流到已处理部门 | **拒绝操作**并返回具体原因；不产生任何状态变更 |
| 同一节点被回退超过 2 次 | 拒绝再次回退，提示改用驳回或终止 |

## 第8章 接口与集成预留

### 8.1 接口设计原则

- 统一API网关，所有模块通过RESTful API通信。
- 用户/组织架构数据作为主数据源，供后续HR系统调用。
- 审批单归档数据结构标准化，便于后续数据仓库抽取。
- **一期不对外提供写入接口**（OpenAPI 只开放组织与用户的只读查询），避免在权限模型成熟前引入外部写入风险。

### 8.2 合同管理系统集成路径

参考开源项目：https://github.com/miyanagaaoi/contract

- **MVP阶段**：合同审批单在OA中完成审批流程，审批通过后由集团办/经发部**人工导出**合同文本归档，不做系统对接。
- **后续阶段**：合同管理系统作为独立模块接入，复用OA的用户体系和审批引擎，通过API实现合同台账与审批流的双向同步。

## 第10章 验收标准

验收标准必须是**可执行、可判定**的。每条包含：前置条件 → 操作 → 可观测结果。边界用例（越权、会签阈值、撤回重提、人员空缺）与主流程用例同等重要。

**试运行退出条件**（满足全部方可全面推广）：

1. 至少 1 家子公司、四类单据各完成 ≥10 笔真实审批；
2. 无 P0/P1 缺陷（**分级定义**：P0 = 阻断上线，如数据错误、越权、流程不可用；P1 = 主流程可用但关键功能异常且无绕行方案；P2 = 有绕行方案的缺陷；P3 = 体验问题）；
3. 出现过至少 1 次驳回重提、1 次加签、1 次转办、1 次并行协同，且均正常闭环（**闭环判定**：单据最终到达终态且轨迹完整）；
4. 审计日志与实际操作可核对（**抽样口径**：随机抽取 20 条操作，逐条可由审计日志还原操作人、时间、对象与变更前后值）。

> **V0.4 决策状态**：Q6（流程闸门次数上限）与 Q7（补件时限）已随本版**定稿关闭**，数值即 9.1 的默认值；Q13（财务部数据域口径）已裁定，见附录 D。

## 第13章 设计规范与UI约定

本章约定系统统一的视觉语言。**完整令牌与组件规范见项目根目录 [`DESIGN.md`](../DESIGN.md)**（遵循 [Stitch DESIGN.md 规范](https://stitch.withgoogle.com/docs/design-md/specification/)：YAML 设计令牌 + 组件规则 + 校验项，可直接交给编码智能体生成一致 UI）。本章只记录必须写进需求、影响功能实现的硬约束。

### 13.1 视觉基调

- **白色画布 + 深墨文字 + 单一企业蓝 `#1f5ae0`**：全系统只有一个彩色强调色，仅用于主按钮、文本链接、焦点环、当前选中项四处，不做装饰性用色。
- **左侧深色导航（224px）+ 白色内容区**：深色 `#151a22` 仅属于导航，不侵入业务区；H5 端使用白色顶栏。
- **高数据密度为默认值**：正文 14px、表格行高 44px（紧凑 36px）、控件高 32px；H5 端触控提升至 44px。
- **层级靠细线与表面阶梯**：默认 1px 细线 + 四级表面（白 → `#f7f8fa` → `#f2f4f7` → `#e6e9ef`）；阴影只用于下拉、模态、抽屉。

### 13.2 与审批业务强相关的约定

- **状态色全局唯一**：草稿/已关闭 = 灰、待我审批/超时预警 = 琥珀、审批中 = 蓝、已通过 = 绿、已驳回/终止 = 红。四类单据**不得各自发明状态配色**（对照 `DESIGN.md` 附录B映射表）。
- **金额规则**：金额字段必须为等宽数字（`tnum`）、右对齐、保留两位小数；≥100 万时同时显示万元换算，避免错读。资金审批单金额为 0 或空时禁止提交。
- **一屏一个主按钮**：任何页面/模态/抽屉只允许一个主按钮，避免审批误点。
- **危险操作二次确认**：驳回、终止、加签等操作的确认按钮必须写明动作与对象（如"确认驳回《XX合同审批单》"）。
- **权限不可见优于不可用**：无数据权限的组织节点与单据**不渲染**（而非置灰），防止通过界面探测组织架构（对应 5.2 权限模型）。
- **电子签名不可删除**：签名图、时间戳与审批单绑定存储，仅可重新签署并保留历史版本（对应 6.5）。
- **H5 约定**：触控目标 ≥44px，底部操作栏 60px 常驻并适配安全区；页面叠加"姓名+工号"水印（5%–8% 透明度、-24° 旋转），水印不得遮挡按钮与表单值（对应 6.8）。
- **三态读写模型的唯一例外**：印鉴证照审批单的「归还状态 / 归还日期」在**审批中可由发起人与节点⑦（归档登记）修改**，其余主字段一律只读；补件期间同样只读（见 `forms.md` 1.2）。
- **审批中心布局**：采用**「全宽数据表 + 浮层详情」**——列表为整页表格（列全展开，含"当前节点"列，44px 行高、表头粘滞），点击行弹出居中浮层查看单据详情与审批记录（主表单 2fr / 审批记录 1fr）。**不做列合并、不做常驻详情栏**，以保留纵向比对能力（金额 / 节点 / 时间的多列对照）。
  - 数据比对型页面（审计日志用 36px 紧凑行）**同样用表格**；移动端 H5 用卡片列表（44px 触控）。
  - 规范细节见 `DESIGN.md`「Grid & Container」与「Panel 布局令牌」。

### 附录B：流程状态机

```
                        ┌──────────────── 撤回（仅节点②通过前）────────────────┐
                        │                                                    │
   [草稿] ──提交──> [审批中] ──全部节点通过──> [已通过]（终态，归档）
      ^                 │  ↑
      │                 │  └── 补件完成（回到请求补件的节点）── [待补件]（子状态）
      │                 │                                          ↑
      │                 ├── 任一节点要求补充材料 ──────────────────┘
      │                 ├──任一节点驳回──> [已驳回] ──发起人修改重提──> [审批中]
      │                 │                      │                        （重新解析审批人快照、
      │                 │                      └── 发起人放弃 ──> [已撤回]（回到草稿）
      │                 └──管理员/集团分管领导终止──> [已终止]（终态，不可再提交）
      └──────────────────────── 已撤回 / 已驳回 可回到草稿
```

> **撤回口径（V0.4 澄清）**：撤回**只发生在节点②通过之前**（REQ-FLOW-009）；已驳回后发起人放弃同样回到草稿，不产生新的审批分支。`flow_instance.status` 的 `withdrawn` 之后实例回到 `draft`（草稿），可修改后重新提交（重新解析审批人快照）。

> 「待补件」是 `flow_instance.sub_status`，实例主状态仍为「审批中」——补件不是驳回，统计口径不受污染（见 7.2）。
> 「流转 / 回退上一节点 / 回到本部门」**不改变实例状态**，只改变当前节点与承接部门，记录在 `flow_routing`。

**节点实例状态**：`未开始` → `进行中` → `等待补件` → `已通过` / `已驳回` / `已跳过` / `已退回` / `已取消`

**任务状态**：`待处理` → `已同意` / `已拒绝` / `已转办` / `已改派` / `已加签` / `已流转` / `已回退` / `已请求补件` / `已自动关闭`

**联动规则**见 7.2 表格（驳回、会签达标、或签通过、实例终态、跳过、补件请求与提交、流转与回退、上限拒绝）——这些规则必须在引擎层统一实现，不允许各页面自行处理。
